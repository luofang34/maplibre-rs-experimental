maplibre-rs (experimental fork) Documentation

Introduction

maplibre-rs is a portable and performant vector and raster maps renderer.

This book documents the experimental fork of maplibre-rs. Its API documentation is published alongside this book.

Name

The name of the library is “maplibre-rs”. The camel-case version of it is “MapLibreRs”.

maplibre runs across desktop, browser, mobile, spatial/XR, and headless server environments on top of wgpu.

Feature Flags (maplibre)

The core maplibre crate keeps platform I/O and optional subsystems modular so embedded, WebAssembly, and custom-loader hosts pull only what they need:

  • native-io (enabled by default) — enables Tokio (platform/noweb), reqwest, reqwest-middleware, and HTTP disk caching (http-cache-reqwest). Disabling default features (--no-default-features) compiles maplibre cleanly without native socket or TLS crates.
  • raster (enabled by default) — enables raster imagery tile decoding, upload, and rendering (RasterPlugin).
  • geojson (enabled by default) — enables inline/URL GeoJSON source parsing, clustering, and tessellation (GeoJsonPlugin).
  • mlt (enabled by default) — decodes MapLibre Tiles (.mlt) alongside classic Mapbox Vector Tiles (.mvt / .pbf).
  • headless — enables maplibre::headless (HeadlessMap, HostGpu, SharedMapAssets, MultiViewFrame, and PNG readback). Works both with native-io and with --no-default-features --features headless using a custom ResourceLoader.
  • experimental (opt-in) — enables experimental spatial/astronomical plugins (celestial, starfield, and overlay).
  • web-webgl — configures wgpu limits and downlevel compatibility for WebGL2 contexts on wasm32-unknown-unknown.
  • thread-safe-futures — requires Send bounds on Scheduler and HttpClient futures for multi-threaded native hosts (omitted on single-threaded wasm32).
  • pmtiles — supports HTTP range-request reading from single-file .pmtiles archives.
  • trace — emits tracing spans per schedule stage and render pass for profiling.

Desktop Quickstart (maplibre-winit)

Add maplibre and maplibre-winit to your binary crate and call maplibre_winit::run_headed_map:

use std::path::PathBuf;

use maplibre::{render::settings::WgpuSettings, style::Style};
use maplibre_winit::{run_headed_map, HeadedMapOptions, WinitMapWindowConfig};

const STYLE_URL: &str = "https://demotiles.maplibre.org/style.json";

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let mut style: Style = maplibre::platform::run_multithreaded(async {
        reqwest::get(STYLE_URL).await?.json().await
    })?;
    style.center = Some([-74.006, 40.7128]);
    style.zoom = Some(11.0);
    for (index, layer) in style.layers.iter_mut().enumerate() {
        layer.index = index as u32 + 1;
    }

    let options = HeadedMapOptions {
        max_pitch_degrees: 75.0,
        show_navigation_controls: true,
        ..HeadedMapOptions::default()
    };

    run_headed_map(
        Some(PathBuf::from("./maplibre-cache")),
        WinitMapWindowConfig::new("MapLibre Quickstart".to_string()),
        WgpuSettings::default(),
        style,
        options,
    )?;
    Ok(())
}

Runtime Options (HeadedMapOptions)

HeadedMapOptions configures host behaviour not carried by the MapLibre Style JSON:

  • max_frames: Option<u64> — exits cleanly after rendering a fixed number of frames (useful for smoke tests).
  • max_pitch_degrees: f64 — clamps maximum camera tilt (DEFAULT_MAX_PITCH by default; raised automatically to 85° when style.terrain or Globe projection is active unless overridden).
  • debug_tiles: bool — installs DebugPlugin to draw tile borders and coordinates.
  • show_navigation_controls: bool — toggles the interactive compass/zoom HUD in the top-right corner.
  • zoom_sensitivity: f64 — scales wheel and trackpad zoom speed (1.0 matches MapLibre GL JS).
  • edge_scroll_enabled: bool and edge_scroll_speed_px_per_sec: f64 — enables cursor-at-window-edge panning.

Custom Plugins and Live Mutations (HeadedMapHost & MapHandle)

Use run_headed_map_with and HeadedMapHost when your application registers custom Plugins or configures the Map once initialized:

use std::path::PathBuf;

use maplibre::{render::settings::WgpuSettings, style::Style};
use maplibre_winit::{
    run_headed_map_with, HeadedMapHost, HeadedMapOptions, WinitMapWindowConfig,
};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let host = HeadedMapHost::default().with_configure(|map| {
        let _ = map.set_global_state("theme", serde_json::json!("day"));
    });

    run_headed_map_with(
        None::<PathBuf>,
        WinitMapWindowConfig::new("Configured Map".to_string()),
        WgpuSettings::default(),
        Style::default(),
        HeadedMapOptions::default(),
        host,
    )?;
    Ok(())
}

While a map is running (on desktop or in the browser via web::run_map), callers interact with it through a clonable MapHandle<E>:

  • map.call(|map| map.set_paint_property(layer, name, value)).await updates paint properties, layout visibility, layer filters (set_filter), feature state (set_feature_state), global state (set_global_state), or inline GeoJSON (set_geojson_data) in place without rebuilding unaffected layers.
  • map.call(|map| map.fly_to(camera, curve)).await starts smooth camera flights, and map.until(|map| ...) awaits frame-driven conditions such as flight arrival.
  • map.call(|map| map.query_rendered_features(geometry, &options)).await queries visible vector and symbol features.

Headless Rendering (maplibre::headless)

Enable the headless feature on maplibre to render maps to PNG buffers, host GPU textures (HostGpu), or synchronized multi-view slots (MultiViewFrame) without a display server:

[dependencies]
maplibre = { version = "0.1.0", features = ["headless"] }

create_headless_renderer(width, height, cache_path) initializes an offscreen Kernel and Renderer (backed by Metal on macOS, DX12/Vulkan on Windows, or Vulkan/Lavapipe on Linux CI), and HeadlessMap renders deterministic frames once all requested tiles settle.

See the Examples chapter for 22 runnable style, terrain, globe, clustering, heatmap, and interactive MapHandle examples.

Examples

Each example reproduces the map of a MapLibre GL JS example with maplibre-rs compiled to WebAssembly.

A map starts from a style document. Where GL JS calls addSource and addLayer once the style has loaded, an example adds the same source and layer to the document before the map starts. Each example module exports a function returning the document, which the embedded page passes to startMapLibre. startMapLibre resolves to the running map, whose methods carry GL JS’s names, such as flyTo, setPaintProperty and queryRenderedFeatures, and return promises that settle once the map has applied them; an interactive example also exports a run function that the page calls with the map:

import { startMapLibre } from 'maplibre-rs'
import style, { run } from './fly-to-a-location.js'

const map = await startMapLibre(undefined, undefined, JSON.stringify(await style()))
run(map)

Natively, the demo opens a document saved as JSON:

cargo run -p maplibre-demo -- headed --style style.json

The map reports click and mousemove through map.on, with the point in CSS pixels that queryRenderedFeatures takes. Popups and markers of the GL JS examples are left out.

The Rust tab of an interactive example drives the map from Rust in the browser, through the handle that web::run_map resolves to.

    style.zoom = Some(1.0);

        layer.index = index as u32 + 1;
    }
    style

    Ok(())
}

    style.zoom = 1; // starting zoom

Display Buildings in 3D

Use extrusions to display buildings’ height in 3D.

use std::path::PathBuf;

use maplibre::{
    projection::{ProjectionSpecification, ProjectionType},
    render::settings::WgpuSettings,
    style::{
        layer::{FillExtrusionPaint, LayerPaint, StyleLayer, StyleProperty},
        source::{Source, VectorSource},
        Style,
    },
};
use maplibre_winit::{run_headed_map, HeadedMapOptions, WinitMapWindowConfig};
use serde_json::json;

const BASE_STYLE_URL: &str = "https://tiles.openfreemap.org/styles/bright";

pub fn build_style(mut style: Style) -> Style {
    style.projection = Some(ProjectionSpecification {
        projection_type: ProjectionType::Globe,
    });
    style.center = Some([-74.0066, 40.7135]);
    style.zoom = Some(15.5);
    style.pitch = Some(45.0);
    style.bearing = Some(-17.6);

    let building_source = if style.sources.contains_key("openmaptiles") {
        "openmaptiles".to_string()
    } else {
        style.sources.insert(
            "openfreemap".to_string(),
            Source::Vector(VectorSource {
                url: Some("https://tiles.openfreemap.org/planet".to_string()),
                ..Default::default()
            }),
        );
        "openfreemap".to_string()
    };
    style.layers.retain(|layer| layer.id != "building-top");

    // Insert the layer beneath the first symbol layer with labels.
    let label_layer_index = style
        .layers
        .iter()
        .position(|layer| {
            matches!(
                &layer.paint,
                Some(LayerPaint::Symbol(symbol)) if symbol.text_field.is_some()
            )
        })
        .unwrap_or(style.layers.len());

    style.layers.insert(
        label_layer_index,
        StyleLayer {
            id: "3d-buildings".to_string(),
            type_: "fill-extrusion".to_string(),
            source: Some(building_source),
            source_layer: Some("building".to_string()),
            minzoom: Some(14.0),
            filter: Some(json!(["!=", ["get", "hide_3d"], true])),
            paint: Some(LayerPaint::FillExtrusion(FillExtrusionPaint {
                fill_extrusion_color: Some(StyleProperty::parse(&json!([
                    "interpolate",
                    ["linear"],
                    ["get", "render_height"],
                    0,
                    "lightgray",
                    200,
                    "royalblue",
                    400,
                    "lightblue"
                ]))),
                fill_extrusion_height: Some(StyleProperty::parse(&json!([
                    "interpolate",
                    ["linear"],
                    ["zoom"],
                    14,
                    0,
                    14.5,
                    ["get", "render_height"]
                ]))),
                fill_extrusion_base: Some(StyleProperty::parse(&json!([
                    "interpolate",
                    ["linear"],
                    ["zoom"],
                    14,
                    0,
                    14.5,
                    ["get", "render_min_height"]
                ]))),
                fill_extrusion_opacity: Some(StyleProperty::parse(&json!([
                    "interpolate",
                    ["linear"],
                    ["zoom"],
                    14,
                    0,
                    14.5,
                    1
                ]))),
                ..Default::default()
            })),
            ..Default::default()
        },
    );

    for (index, layer) in style.layers.iter_mut().enumerate() {
        layer.index = index as u32 + 1;
    }
    style
}

    let base: Style = maplibre::platform::run_multithreaded(async {
        reqwest::get(BASE_STYLE_URL).await?.json().await
    })?;
    let style = build_style(base);

    run_headed_map(
        Some(PathBuf::from("./maplibre-cache")),
        WinitMapWindowConfig::new("Display Buildings in 3D".to_string()),
        WgpuSettings::default(),
        style,
        HeadedMapOptions::default(),
    )?;

/// Flies an active map handle to `[lng, lat]` and reports whether the camera arrived there.
pub async fn fly_camera(
    map: &MapHandle<CurrentEnvironment>,
    [lng, lat]: [f64; 2],
) -> Result<bool, JSError> {
    let destination = CameraOptions {
        center: Some(LatLon::new(lat, lng)),
        ..Default::default()
    };
    let flight = map
        .call(move |map| map.fly_to(destination, FlightCurve::Fly(FlyOptions::default())))
        .await??;
    // Asked again after every frame until the move ends.
    let arrived = map
        .until(move |map| match map.flight_outcome(flight) {
            FlightOutcome::Flying => None,
            outcome => Some(outcome == FlightOutcome::Arrived),
        })
        .await?;
    Ok(arrived)
}

    destination: [f64; 2],
) -> Result<bool, JSError> {
    let map = web::run_map(new_worker, build_style(base), WebMapHost::default()).await?;
    fly_camera(&map, destination).await
}

/// Moves the point to where the International Space Station is now, and the camera with it.
pub async fn update(map: &MapHandle<CurrentEnvironment>) -> Result<(), Box<dyn std::error::Error>> {
    let body: Value = reqwest::get(ISS_URL).await?.json().await?;
    let longitude = body["longitude"]
        .as_f64()
        .ok_or("missing numeric `longitude` field")?;
    let latitude = body["latitude"]
        .as_f64()
        .ok_or("missing numeric `latitude` field")?;
    let point = json!({
        "type": "Feature",
        "properties": {},
        "geometry": {"type": "Point", "coordinates": [longitude, latitude]}
    });
    let camera = CameraOptions {
        center: Some(LatLon::new(latitude, longitude)),
        ..Default::default()
    };
    map.call(move |map| {
        map.set_geojson_data("iss", GeoJsonData::Inline(Arc::new(point)))?;
        map.fly_to(
            camera,
            FlightCurve::Ease {
                duration: std::time::Duration::from_secs(1),
            },
        )
    })
    .await??;
    Ok(())
}

pub async fn follow(map: MapHandle<CurrentEnvironment>) {
    while !map.is_closed() {
        if let Err(error) = update(&map).await {
            tracing::warn!(%error, "the station's position could not be shown");
        }
        let delay = js_sys::Promise::new(&mut |resolve, _| {
            if let Some(window) = web_sys::window() {
                window
                    .set_timeout_with_callback_and_timeout_and_arguments_0(&resolve, 2000)
                    .ok();
            }
        });
        wasm_bindgen_futures::JsFuture::from(delay).await.ok();
    }
}

Development Guide

Running maplibre-rs demos on various platforms

During development, you will want to run the maplibre demos on your local machine to test out your changes. There are multiple demos of maplibre-rs for different targets. Some targets have prerequisites depending on your operating system.

  • maplibre-demo - targets Windows, macOS and Linux, it is built directly with cargo.
  • apple - targets iOS and macOS and relies on the xcode IDE (apple/visionos targets Apple Vision Pro via C ABI + Metal).
  • android - targets 64-bit Android devices and emulators (arm64-v8a and x86_64, minSdk 23) in Android Studio / Gradle.
  • web - targets browsers via WebAssembly (wasm32-unknown-unknown) with WebGPU and WebGL2 backends.
  • maplibre (--features headless) - renders maps offscreen without a windowing system via maplibre::headless::map::HeadlessMap (used by server rendering, multi-view hosts, and the render-tests conformance runner).

All the targets below require you to install rustup to manage your Rust toolchain.

Note: Make sure you have selected the right toolchain target within rustup. You can use rustup show to see your active toolchain. If you want to change the target of the build manually, use the cargo --target parameter.

Maplibre-demo

Linux/macOS

The build for desktop is very simple, you just have to run the following command from the root of the maplibre-rs project:

cargo run -p maplibre-demo

To view the bundled world style on a globe, or your own style, use the headed options:

Left-drag pans, the mouse wheel or +/- zooms around the pointer, right-drag or middle-drag rotates and tilts, and W/A/S/D or the arrow keys pan along the camera’s current heading (hold Shift for 2.5× turbo speed). On macOS trackpads, two-finger scrolling pans the map (like Apple Maps), pinch zooms, two-finger rotate turns the compass bearing, and Option + two-finger drag tilts/orbits. A floating GPU navigation HUD in the top-right corner provides one-click access to the 3D Compass, 2D/3D (AUTO tilt), +/- zoom, Home, and MAP/RTS control modes (where RTS mode enables Red Alert-style screen-edge scrolling and right-click panning). --frames <n> closes the window after n frames.

Development Documents

Architecture

maplibre is structured as a modular, data-oriented rendering engine tailored specifically to slippy-map tile pyramids, 3D terrain, planetary globes, and stereo XR views. Every major subsystem lives inside maplibre/src/ with zero unsafe code in the renderer (#![forbid(unsafe_code)] in maplibre::render) and strict fallible error propagation across initialization and frame execution.

flowchart LR
    Host["Host (winit / Web / Headless / visionOS)"] --> Handle["MapHandle / Map"]
    Handle --> Schedule["Schedule (Ordered Stages)"]
    Schedule --> World["TCS World (Resources + Tiles)"]
    Schedule --> APC["AsyncProcedureCall (Workers)"]
    APC --> Loader["SourceClient & SharedLoader"]
    APC -->|Transferables| World
    Schedule --> Graph["RenderGraph & UploadQueue"]
    Graph --> WGPU["wgpu (Metal / Vulkan / DX12 / WebGPU / WebGL2)"]

1. Tile Component System (maplibre::tcs)

Early prototypes experimented with general-purpose Entity-Component-System (ECS) frameworks, which added archetype fragmentation and indirection without matching the natural key of a map engine: hierarchical tile coordinates (WorldTileCoords).

maplibre::tcs replaces generic ECS storage with a domain-specific Tile Component System (TCS):

  • World pairs two stores under one ownership root:
    • Resources — singleton typed state (ViewState, Style, WgpuTileViewPattern, TerrainResources, FrameTimings, lighting, global state) keyed by TypeId.
    • Tiles — per-tile typed TileComponent attachments (VectorLayersDataComponent, RasterLayersDataComponent, DemTileComponent, symbol/SDF layout data, missing-layer markers) indexed by WorldTileCoords inside a spatial quadtree/pyramid (tcs::pyramid).
  • Borrow-checked queries: GlobalQueryState and EphemeralQueryState track shared and mutable TypeId borrows dynamically when a system runs, preventing aliasing without unsafe code.
  • Typed errors: every system implements System (fn run(&mut self, context: &mut MapContext) -> Result<(), SystemError>), returning structured failures rather than panicking.

2. Schedule, Stages, and Fallible Plugins

Frame execution is driven by Schedule, an ordered list of labeled Stages operating on MapContext (World, Style, ViewState, Renderer).

Default Frame Stages (RenderStageLabel)

RenderPlugin installs seven deterministic stages in Schedule:

  1. Input — applies host viewport/cursor input, drains MapCommands from MapHandles, and advances camera flights (fly_to / ease_to) so every downstream system observes the resolved ViewState (or stereo XrFrame / multi-view slot).
  2. Request — computes the visible tile covering (including globe horizon culling, terrain elevation bounds, XR frustum union, and flight PrefetchView), dispatches missing vector/raster/DEM fetches through AsyncProcedureCall, and ingests completed worker results into World.tiles.
  3. Prepare — creates or resizes GPU attachments, compiles demand-driven shaders/pipelines (PipelineCache), prepares glyph/sprite atlases, and writes per-frame view/globe/lighting uniforms.
  4. Queue — uploads newly arrived vertex/index/instance/texture payloads through UploadQueue and populates RenderPhase queues (TileMaskItem, LayerItem, TranslucentItem, DrapePhase).
  5. PhaseSort — sorts phase items into deterministic MapLibre layer and depth order and harvests completed GPU timestamp queries (gpu_timer).
  6. Render — executes RenderGraph passes, submits command buffers, and presents swapchain or eye targets.
  7. Cleanup — marked with Schedule::run_after_failure so per-frame phase queues are cleared and out-of-budget tiles are evicted even if an earlier stage returned a StageError.

Missing prerequisite stages, render-graph edges, or GPU allocation failures surface cleanly as PluginError.

3. GPU Architecture: RenderGraph, BufferPool, and UploadQueue

  • RenderGraph orders render passes explicitly by slot dependencies:
    • DrapePassNode (when 3D terrain is active) renders drapeable fill, line, raster, hillshade, and color-relief layers into pooled per-tile offscreen textures (DrapePhase).
    • MainPassNode renders sky/starfield/atmosphere, terrain meshes or stencil-masked 2D/globe tiles, 3D fill-extrusions, circles, heatmaps, and crisp screen-space SDF symbols/labels.
    • DepthCopyNode & TranslucentPassNode copy resolved depth when needed and composite order-dependent translucent overlays and custom PassHooks.
  • BufferPool sub-allocates tile vertex, index, and feature-paint slices inside large backing wgpu::Buffer arenas, avoiding per-tile buffer allocation churn and minimizing bind-group switches.
  • Counted UploadQueue: Renderer wraps wgpu::Queue inside UploadQueue, which atomically counts every byte written via write_buffer, write_texture, create_buffer_init, and create_texture_with_data. Direct calls to uncounted wgpu::Queue upload methods are denied workspace-wide via clippy.toml, ensuring frame traces and upload budgets remain exact.
  • In-place GPU style & state refresh: style mutations (set_paint_property, set_layout_property, set_filter, set_feature_state, set_global_state) classify what changed (style::mutation). Data-driven paint and feature-state updates re-evaluate only the affected per-feature paint attributes and rewrite their BufferPool ranges via UploadQueue—without re-fetching or re-tessellating tile geometry.

4. Source I/O, ResourceLoader, and AsyncProcedureCall (APC)

Kernel<E> decouples the engine from the host OS or browser through the Environment trait:

  • ResourceLoader & SourceClient (maplibre::io): deduplicates in-flight HTTP, pmtiles://, asset://, and inline data requests across the map thread and all worker threads (SharedLoader), applying bounded concurrency (tile_backpressure) and exponential retry (tile_retry).
  • AsyncProcedureCall (APC): offloads CPU-heavy MVT/MLT decoding, GeoJSON clustering, expression pre-evaluation, Lyon polygon/line tessellation, glyph SDF rasterization, and raster-dem decoding off the render thread:
    • Native (SchedulerAsyncProcedureCall): schedules tasks onto a multi-threaded Tokio pool and passes decoded Rust structs (DefaultVectorTransferables, DefaultDemTransferables) back with zero serialization overhead.
    • Web (wasm32): dispatches jobs to dedicated Web Workers, serializing geometry into zero-copy FlatBuffers (FlatBufferTransferable) transferred via ArrayBuffer ownership transfer (or shared linear memory on multithreaded Wasm builds).

5. HeadlessMap, Multi-View, 3D Terrain, Atmosphere & Stereo XR

  • HeadlessMap & Multi-View (maplibre::headless): drives deterministic offscreen rendering, shares immutable decoded tiles, sprites, glyphs, and compiled GPU pipelines across independent map worlds via SharedMapAssets, and renders multiple synchronized camera slots (MultiViewFrame, ViewSlotId) in a single tick.
  • 3D Terrain (maplibre::terrain): decodes Mapbox and Terrarium raster-dem tiles into GpuDemPool, stitches level-of-detail seams with backfill_neighbours and configurable TerrainSkirts, closes polar caps on globes via PolarPoleElevations, drapes vector/raster layers via RTT caching (DrapeBudget), and supports exact CPU elevation queries and ray-terrain intersection (TerrainHit, sightline).
  • Globe, Atmosphere & Celestial (maplibre::projection, maplibre::celestial, maplibre::starfield): smoothly transitions between Web Mercator and 3D Globe projection, shading atmospheric limb scattering, twilight bands, solar/lunar discs, eclipses, and Hipparcos starfields in ECEF coordinates.
  • Stereo XR (maplibre::render::xr & apple/visionos): evaluates tile coverings across the union of left and right eye frustums (XrFrame, ScenePlacement) and renders stereo colour + reverse-Z Depth32Float eye targets directly into host Metal textures.

Design Principles & Trade-offs

This document records the core engineering decisions behind maplibre and how they shape day-to-day development across maplibre, maplibre-winit, web, and apple/visionos.

1. Domain-Specific TCS Over Generic ECS

Map rendering has a very specific data topology:

  • Global singleton state (Style, ViewState, WgpuTileViewPattern, GpuDemPool, atlases, frame timings).
  • Sparse, hierarchical per-tile components keyed by (z, x, y, build_id) (WorldTileCoords) that are queried along parent/child/ancestor pyramid paths every frame (for overscaled vector fallbacks, DEM ancestor draping, and stencil masking).

Using maplibre::tcs (World, Tiles, Resources) instead of an external archetype ECS gives:

  1. Direct pyramid traversal (tcs::pyramid) without entity-ID hash lookups when resolving ancestor fallback tiles.
  2. Zero-macro system signatures: systems are plain Rust functions or structs implementing System::run(&mut self, &mut MapContext) -> Result<(), SystemError>.
  3. Lightweight WebAssembly footprint: avoids procedural-macro and archetype-table bloat in wasm32-unknown-unknown bundles.

2. Explicit Schedule Stages and Fallible Lifecycle

GPU applications in browsers, mobile apps, and XR headsets routinely face recoverable environment failures: lost GPU surfaces, suspended windows, invalid user styles, or exhausted memory budgets.

  • No non-test panics: production crates enforce #![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic)] alongside scripts/check-panics.mjs in CI.
  • Fallible Plugin::build and Stage::run: plugin installation returns Result<(), PluginError> and frame execution returns StageResult.
  • Guaranteed frame cleanup (Schedule::run_after_failure): RenderStageLabel::Cleanup runs even when an earlier stage errors, ensuring transient per-frame RenderPhase vectors and tile retention budgets never leak across frames.

3. Worker Offload via Environment and Transferables

To hold 60–90+ FPS (especially on Apple Vision Pro where missed CompositorServices deadlines cause visible judder), the render thread performs no network I/O, protobuf/MLT parsing, polygon tessellation, or font glyph rasterization:

  • Environment parameterizes Kernel<E> over MapWindowConfig, AsyncProcedureCall, Scheduler, and OffscreenKernelEnvironment.
  • VectorTransferables, RasterTransferables, and DemTransferables let native builds pass heap-allocated buffers directly across channels while single-threaded Web Worker builds serialize into FlatBuffers transferred via zero-copy postMessage transfer lists.
  • SharedLoader (ResourceLoader) centralizes caching and in-flight request coalescing so simultaneous tile/glyph/sprite requests from multiple workers share one HTTP connection pool and disk cache.

4. In-Place GPU Updates & Byte-Counted Uploads

Re-tessellating an entire vector tile whenever a hover state or theme changes wastes CPU and frame upload bandwidth. Instead:

  1. Expression classification (maplibre::style::expression): every parsed Style Spec expression statically computes output_type(), is_constant(), is_feature_constant(), and is_zoom_constant().
  2. Targeted mutation classification (maplibre::style::mutation):
    • Uniform-only paint changes update GPU uniform bindings in Prepare.
    • Feature-dependent paint, feature-state, or global-state changes re-evaluate feature paint columns (vector::feature_paint) against retained feature properties and write updated byte ranges into BufferPool via UploadQueue::write_buffer.
    • Only layout or structural source changes trigger worker re-processing.
  3. Strict upload accounting: UploadQueue wraps wgpu::Queue and counts every uploaded byte per frame. clippy.toml forbids calling raw wgpu::Queue::write_buffer / write_texture outside UploadQueue, preventing hidden upload spikes.

5. Unified 2D, Globe, 3D Terrain, and Stereo XR Pipeline

Rather than maintaining separate renderers for 2D Mercator, 3D globes, terrain, and headsets:

  • Coordinate & projection separation: tile workers always tessellate into normalized tile-local coordinates (0..EXTENT). Vertex shaders project tile vertices into either flat Web Mercator, curved ECEF Globe coordinates, or displaced 3D raster-dem meshes, transitioning continuously across zoom levels.
  • Hybrid terrain draping: flat fill/line/raster layers drape onto 3D terrain via cached render-to-texture (DrapePassNode + DrapeBudget), while 3D extrusions (fill-extrusion) and screen-aligned symbol labels render directly in the main pass at sampled terrain elevations so vertical walls and crisp text never blur on steep slopes.
  • View abstraction (ResolvedFrameView & XrFrame): a standard window renders a single ViewState; MultiViewFrame iterates over N named ViewSlotId cameras; and XrFrame renders N eyes (XrEye) from a shared ScenePlacement while computing tile requests once across the combined stereo frustum.

6. Ratcheted Conformance & Static Architecture Guards

Correctness and architectural hygiene are enforced continuously in CI:

  • MapLibre Style Spec Conformance: render-tests runs 1,700+ pixel (expected.png) and query (expected.json) fixtures on software Vulkan (lavapipe) with a ratcheted render-tests/ignores.json baseline (any unexpected failure or unremoved newly-passing ignore fails CI), complemented by maplibre/tests/expression_conformance.rs.
  • Static guards: scripts/check-file-length.mjs (<= 500 lines per .rs file), scripts/check-module-layout.py (no mod.rs), scripts/check-panics.mjs, scripts/check-wasm-deps.py (forbids native OS/runtime/TLS crates in wasm32-unknown-unknown trees), and cargo-deny (deny.toml) keep crate boundaries clean as the engine grows.

Caching

The caching for maplibre-rs is handled on the networking layer. This means that data which is fetched over slow IO is cached in the format of the network requests. The maplibre-rs library is not introducing a separate serialization format for caching.

Instead, caching functionality of HTTP client libraries of the web platform are used. This has the advantage that we can honor HTTP headers which configure caching. This is very important for fetched tiles, as they can have an expiry date.

  • On the web the browser is automatically caching raw tiles.
  • On Linux, macOS, iOS and Android we are utilizing reqwest-middleware-cache, which writes raw network requests to disk.

visionOS

The standalone apple/visionos crate packages maplibre as a static C archive (libmaplibre_visionos.a) paired with apple/visionos/maplibre_visionos.h for Swift and CompositorServices applications on Apple Vision Pro (MapLibreVision).

Unlike windowed winit targets, visionOS ImmersiveSpace rendering is driven by Apple’s LayerRenderer frame loop. The host owns the MTLDevice and per-eye drawable textures, and hands them across the C ABI each frame with zero CPU readback.

Building & Checking

The visionOS targets (aarch64-apple-visionos and aarch64-apple-visionos-sim) are Tier 3 Rust targets and build standard library crates from source via -Z build-std=std,panic_abort using the nightly toolchain pinned in apple/visionos/rust-toolchain.toml:

# Typecheck and lint both device and simulator targets (matches CI):
just check-visionos

# Build release static libraries for simulator and device:
cargo +nightly build --manifest-path apple/visionos/Cargo.toml \
    -Z build-std=std,panic_abort --release --target aarch64-apple-visionos-sim
cargo +nightly build --manifest-path apple/visionos/Cargo.toml \
    -Z build-std=std,panic_abort --release --target aarch64-apple-visionos

The MapLibreVision Xcode project invokes apple/visionos/MapLibreVision/Scripts/build-rust.sh before linking to build the matching slice automatically.

C ABI Overview (maplibre_visionos.h)

All functions in maplibre_visionos.h catch Rust panics at the FFI boundary, return explicit status codes (0 on success, negative codes on invalid arguments, initialization failure, or frame error), and document ownership of every pointer.

Shared Metal Device & Queue

  • maplibre_visionos_new(metal_device, style_json, width, height, sample_count) / maplibre_visionos_new_configured(..., config) wrap the caller’s id<MTLDevice> inside wgpu_hal::api::Metal via HostGpu so maplibre and the host Swift renderer share one GPU device and pipeline cache without copying textures across APIs.
  • maplibre_visionos_command_queue(map) returns the unretained id<MTLCommandQueue> wgpu submits on. Submitting the host’s post-processing and LayerRenderer.Drawable.encodePresent on this same queue guarantees FIFO execution after map passes without CPU stalls.
  • MaplibreVisionOSConfig configures cache_dir (disk HTTP cache), bundle_dir (offline asset:// tile/glyph/sprite lookup), color_srgb (BGRA8UnormSrgb for LayerRenderer, BGRA8Unorm for offscreen/UI), and skirts (MAPLIBRE_VISIONOS_SKIRTS_NONE or AUTO).

Stereo XrFrame & ScenePlacement

maplibre_visionos_render_stereo drives HeadlessMap::render_xr (maplibre::render::xr::XrFrame):

  • MaplibreVisionOSPlacement maps directly to ScenePlacement:
    • anchor: geographic lon_deg, lat_deg, and altitude_m standing at the origin of the map’s local East-North-Up scene frame.
    • world_from_scene: column-major 4x4 rigid + uniform-scale transform from scene metres into LayerRenderer tracking space. Tabletop globes and room-scale terrain use the exact same renderer; transitioning between them only updates world_from_scene.
  • prefetch: optional destination MaplibreVisionOSPlacement during an animated camera flight. PrefetchView requests destination tiles ahead of arrival without requesting intermediate zoom levels swept through mid-flight.
  • request_overscan: factor (>= 1.0) expanding each eye’s frustum tangents for tile selection so head rotation finds neighbouring tiles already resident in VRAM.
  • MaplibreVisionOSEye (eyes[0..eye_count]):
    • world_from_eye: column-major 4x4 eye-to-world pose (deviceAnchor.originFromAnchorTransform * view.transform).
    • left_tan, right_tan, up_tan, down_tan (positive half-angle tangents from LayerRenderer.Clock / View.tangents) and near_m, far_m in world metres.
    • color_texture: id<MTLTexture> (bgra8Unorm or bgra8Unorm_srgb, created with .shaderWrite / .renderTarget and .pixelFormatView when LayerRenderer supplies a typeless/sRGB pair).
    • msaa_texture: optional multisample id<MTLTexture> resolved into color_texture.
    • depth_texture: optional Depth32Float id<MTLTexture> receiving reverse-Z depth (1.0 at near, 0.0 at far) for visionOS compositor reprojection and hand occlusion.

Windowed Orbit Camera & Spatial Raycasting

For volumetric or 2D window scenes alongside an ImmersiveSpace:

  • maplibre_visionos_render_orbit renders a single colour + optional depth target from MaplibreVisionOSOrbitCamera (center_lon_deg, center_lat_deg, distance_m, pitch_deg, bearing_deg, fov_y_deg).
  • maplibre_visionos_screen_to_ground, maplibre_visionos_drag_orbit, and maplibre_visionos_move_anchor_to_screen project gaze/pinch rays onto the 3D terrain surface or reference sphere/ellipsoid.

Terrain, Planetary Bodies & Celestial Environment

  • maplibre_visionos_terrain_elevation(map, lon_deg, lat_deg, &out_meters) samples loaded raster-dem tiles synchronously on the map thread for anchoring spatial pins and labels onto 3D relief.
  • maplibre_visionos_set_body switches planetary radius, terrain exaggeration, polar cap elevations (PolarPoleElevations), and procedural relief presets (Earth, Moon, Mars).
  • maplibre_visionos_set_sky and maplibre_visionos_set_stars feed ECEF sun/moon vectors (maplibre::celestial::EcefDirection), twilight bands, eclipse fractions, and stellar catalogues (maplibre::starfield) into the atmosphere and starfield passes.
  • maplibre_visionos_register_image_provider and maplibre_visionos_invalidate_images register C callbacks resolving missing namespace:name style icons on demand (e.g., SF Symbols rasterized on the Swift side).

  • Memory pressure: maplibre_visionos_set_available_memory(map, available_bytes) feeds os_proc_available_memory() into maplibre::render::memory_budget, tightening tile cache retention before visionOS jetsams the process.
  • Frame timeline tracing: maplibre_visionos_trace_enable, maplibre_visionos_trace_span, maplibre_visionos_trace_presentation, maplibre_visionos_trace_device, and maplibre_visionos_trace_export record CPU/GPU stage timings, per-frame upload bytes, LayerRenderer presentation intervals, and thermal state to JSON.

Web

The browser distribution lives in web/ (the Rust wasm32-unknown-unknown cdylib/rlib crate) and web/lib/ (the TypeScript host wrapper and build.mjs bundler). Instead of wasm-pack, Webpack, or Parcel, packaging is driven directly by web/lib/build.mjs using cargo, wasm-bindgen, wasm-opt (binaryen), esbuild, and tsc.

Build Pipeline (web/lib/build.mjs)

Running just web-lib build (or node build.mjs inside web/lib/) executes five deterministic stages:

  1. Exact wasm-bindgen-cli version check (checkWasmBindgenVersion): Reads the exact pinned wasm-bindgen = "=..." version from the workspace Cargo.toml and verifies wasm-bindgen --version matches before compiling, preventing subtle JS/Wasm ABI mismatches.

  2. Rust compilation (cargo build --target wasm32-unknown-unknown): Builds web with --profile wasm-dev (default) or --profile wasm-release (--release):

    • WebGPU (default): compiles web against wgpu’s WebGPU backend.
    • WebGL2 (--webgl): passes --features web-webgl to enable wgpu WebGL2 support and downlevel limits.
    • Multithreaded shared-memory workers (--multithreaded): passes -Z build-std=std,panic_abort and configures target.wasm32-unknown-unknown.rustflags with:
      • -C target-feature=+atomics,+bulk-memory,+mutable-globals
      • -C link-args=--shared-memory --import-memory --max-memory=209715200
      • -C link-args=--export=__heap_base --export=__wasm_init_tls --export=__tls_size --export=__tls_align --export=__tls_base

  3. wasm-bindgen & automated compatibility checks: Runs wasm-bindgen --target web --typescript --out-name maplibre --out-dir src/wasm (plus --debug in dev mode). Using --target web preserves wasm_bindgen::module() so compiled WebAssembly.Module handles can be posted directly to Web Workers. Immediately after binding generation, build.mjs runs node --test test/wasm-instance.test.mjs test/webgpu-compat.test.mjs to validate Wasm instantiation and WebGPU adapter/descriptor compatibility.

  4. Release binary optimization (wasm-opt): When --release is passed, optimizes src/wasm/maplibre_bg.wasm in place via wasm-opt -O (provided by the binaryen npm devDependency).

  5. JavaScript bundling (esbuild) & TypeScript declarations (tsc): Bundles src/index.ts for platform: "browser" with define: { WEBGL, MULTITHREADED }, assetNames: "assets/[name]", and two plugins:

    • esbuild-plugin-inline-worker — bundles and inlines Web Worker entrypoints (both message-passing FlatBufferTransferable workers and shared-memory pool workers) as ES2022 CJS worker blobs so consumers do not have to configure separate worker asset routes.
    • @chialab/esbuild-plugin-meta-url — resolves new URL(..., import.meta.url) references (such as maplibre_bg.wasm) and emits the .wasm binary to dist/esbuild-<format>/assets/ with portable runtime URL resolution.

    Finally, tsc -m es2022 -outDir dist/ts --declaration --emitDeclarationOnly writes TypeScript .d.ts declarations to web/lib/dist/ts/.

Summary

The “RFC” (request for comments) process is intended to provide a consistent and controlled path for new features to enter the map renderer and standard libraries, so that all stakeholders can be confident about the direction the map renderer is evolving in.

This RFC is copied from rust-lang/rfcs. Thanks to everyone who contributed to the Rust RFC process RFC! Thanks for the great inspiration!

Motivation

The freewheeling way that we add new features to maplibre-rs has been good for early development, but for maplibre-rs to become a mature platform we need to develop some more self-discipline when it comes to changing the system. This is a proposal for a more principled RFC process to make it a more integral part of the overall development process, and one that is followed consistently to introduce features to maplibre-rs.

Detailed design

Many changes, including bug fixes and documentation improvements can be implemented and reviewed via the normal GitHub pull request workflow.

Some changes though are “substantial”, and we ask that these be put through a bit of a design process and produce a consensus among the maplibre-rs community.

When you need to follow this process

You need to follow this process if you intend to make “substantial” changes to the maplibre-rs distribution. What constitutes a “substantial” change is evolving based on community norms, but may include the following.

  • Any semantic or syntactic change to the map renderer that is not a bugfix.
  • Removing map renderer features, including those that are feature-gated.

Some changes do not require an RFC:

  • Rephrasing, reorganizing, refactoring, or otherwise “changing shape does not change meaning”.
  • Additions that strictly improve objective, numerical quality criteria (warning removal, speedup, better platform coverage, more parallelism, trap more errors, etc.)
  • Additions only likely to be noticed by other developers-of-maplibre-rs, invisible to users-of-maplibre-rs.

If you submit a pull request to implement a new feature without going through the RFC process, it may be closed with a polite request to submit an RFC first.

What the process is

In short, to get a major feature added to maplibre-rs, one must first get the RFC merged into the RFC repo as a markdown file. At that point the RFC is ‘active’ and may be implemented with the goal of eventual inclusion into maplibre-rs.

  • Fork the repo https://github.com/luofang34/maplibre-rs-experimental
  • Copy rfc/0000-template.md to rfc/0000-my-feature.md (where ‘my-feature’ is descriptive. don’t assign an RFC number yet).
  • Fill in the RFC
  • Submit a pull request. The pull request is the time to get review of the design from the larger community.
  • Build consensus and integrate feedback. RFCs that have broad support are much more likely to make progress than those that don’t receive any comments.

Eventually, somebody on the maplibre-rs team will either accept the RFC by merging the pull request, at which point the RFC is ‘active’, or reject it by closing the pull request.

Who ever merges the RFC should do the following:

  • Assign an id, using the PR number of the RFC pull request. (If the RFC has multiple pull requests associated with it, choose one PR number, preferably the minimal one.)
  • Add the file in the docs/src/rfc/ directory.
  • Create a corresponding issue on maplibre-rs repo
  • Fill in the remaining metadata in the RFC header, including links for the original pull request(s) and the newly created maplibre-rs issue.
  • Communicate that given RFC is now considered ‘active’ on the chat platform of maplibre-rs.
  • Commit everything.

Once an RFC becomes active then authors may implement it and submit the feature as a pull request to the maplibre-rs repo. An ‘active’ is not a rubber stamp, and in particular still does not mean the feature will ultimately be merged; it does mean that in principle all the major stakeholders have agreed to the feature and are amenable to merging it.

Modifications to active RFC’s can be done in followup PR’s. An RFC that makes it through the entire process to implementation is considered ‘complete’; an RFC that fails after becoming active is ‘inactive’.

Alternatives

Retain the current informal RFC process. The newly proposed RFC process is designed to improve over the informal process in the following ways:

  • Discourage non-actionable or vague RFCs
  • Ensure that all serious RFCs are considered equally
  • Give confidence to those with a stake in maplibre-rs development that they understand why new features are being merged

As an alternative, we could adopt an even stricter RFC process than the one proposed here. If desired, we should likely look to Python’s PEP process for inspiration.

Guide-level explanation

Explain the proposal as if it was already included in the project, and you were teaching it to another maplibre-rs user. That generally means:

  • Introducing new named concepts.
  • Explaining the feature largely in terms of examples.
  • Explaining how maplibre-rs users should think about the feature, and how it should impact the way they use maplibre-rs. It should explain the impact as concretely as possible.
  • If applicable, provide sample error messages, deprecation warnings, or migration guidance.
  • If applicable, describe the differences between teaching this to the existing maplibre-rs users and new maplibre-rs users.

For implementation-oriented RFCs (e.g. for internals), this section should focus on how maplibre-rs contributors should think about the change, and give examples of its concrete impact. For policy RFCs, this section should provide an example-driven introduction to the policy, and explain its impact in concrete terms.

Reference-level explanation

This is the technical portion of the RFC. Explain the design in sufficient detail that:

  • Its interaction with other features is clear.
  • It is reasonably clear how the feature would be implemented.
  • Corner cases are dissected by example.

The section should return to the examples given in the previous section, and explain more fully how the detailed proposal makes those examples work.

Rationale and alternatives

  • Why is this design the best in the space of possible designs?
  • What other designs have been considered and what is the rationale for not choosing them?
  • What is the impact of not doing this?

Prior art

Discuss prior art, both the good and the bad, in relation to this proposal. A few examples of what this can include are:

  • Does this feature exist in other map renderers and what experience have their community had?
  • For community proposals: Is this done by some other community and what were their experiences with it?
  • For other teams: What lessons can we learn from what other communities have done here?
  • Papers: Are there any published papers or great posts that discuss this? If you have some relevant papers to refer to, this can serve as a more detailed theoretical background.

This section is intended to encourage you as an author to think about the lessons from other renderers, provide readers of your RFC with a fuller picture. If there is no prior art, that is fine - your ideas are interesting to us whether they are brand new or if it is an adaptation from other map renderers.

Note that while precedent set by other map renderers is some motivation, it does not on its own motivate an RFC.

Unresolved questions

  • What parts of the design do you expect to resolve through the RFC process before this gets merged?
  • What parts of the design do you expect to resolve through the implementation of this feature before stabilization?
  • What related issues do you consider out of scope for this RFC that could be addressed in the future independently of the solution that comes out of this RFC?

Future possibilities

Think about what the natural extension and evolution of your proposal would be and how it would affect the renderer and project as a whole in a holistic way. Try to use this section as a tool to more fully consider all possible interactions with the project and renderer in your proposal. Also consider how this all fits into the roadmap for the project and of the relevant sub-team.

This is also a good place to “dump ideas”, if they are out of scope for the RFC you are writing but otherwise related.

If you have tried and cannot think of any future possibilities, you may simply state that you cannot think of anything.

Note that having something written down in the future-possibilities section is not a reason to accept the current or a future RFC; such notes should be in the section on motivation or rationale in this or subsequent RFCs. The section merely provides additional information.
